### 2026-11-01 — Lobby screens and host hand-over (M2-5b)
- **Host hand-over (owner request):** before the start, `POST /games/:id/host { seat }` moves the host role to another *person* seated in the lobby (a bot, yourself, an empty seat or a non-number seat is refused; host only; 409 after the start). The old host is then an ordinary player and may leave. This **replaces the M2-2 "host can't leave the lobby" decision**: the host still can't leave directly (409 "hand the host role to another player before you leave"), so a lobby always has a host. Mid-game hand-over is M2-13.
- **Settings change in the lobby:** `PATCH /games/:id/settings { settings }` (host, lobby only) merges the sent fields into the current ones and runs the same `parseSettings` checks. The client keeps starter mode valid in one change (turning it on sets saboteur off and events off; turning either back on turns starter mode off), since the server refuses the mix.
- **`uniqueRoles`** is now a lobby setting (default on, label "Unique roles") passed to `GameConfig.uniqueRoles`. Games stored before it existed read as on (the view merges `DEFAULT_SETTINGS`). The saboteur setting is the existing `mole` field, labelled "Saboteur (the dark side)" with Off / Maybe / On.
- **`LobbyView`** also carries `minSeats`, `maxSeats` and the bot personalities (`{ id, name }`), so the client never hard-codes them.
- **Web routes (provisional):** `/new` (host name → `POST /auth/guest` only when not signed in → `POST /games { nickname }`; a signed-in user keeps their session and the nickname is just their seat name in this game, PR #27 review), `/join/:code` (invite page: host + seat count, nickname → join), `/lobby/:id`, `/game/:id` (a placeholder until M2-6). Invite links are `<origin>/join/<code>`; the landing's "Join crew" goes there. The lobby **polls `GET /games/:id` every 2 s** (no lobby socket yet; responses apply in request order so a slow poll never undoes a newer change), and every seated browser moves to `/game/:id` once the status leaves `lobby`. Esc doesn't leave a lobby or a game. Bot seats show a robot badge on the avatar and a "Bot · <personality>" chip. Host actions that hand over or leave use the arm-then-confirm danger button.
- **Playwright runs the server too:** `playwright.config.ts` starts `apps/server` (in-memory PGlite, port 3179) next to Vite, which proxies `/api` to it.

### 2026-11-01 — Scheduler and elastic timing (M2-4)
- **Reconcile, don't schedule by events:** after every change (inside the game's lock, via `liveRoutes`' `onChange`) `planDeadlines(state, timing, now)` lists the deadlines the state calls for, one rule per deadline kind in `DEADLINE_RULES` (a mapped type over the engine's `Deadline["kind"]` plus `scheduleMeeting`, so a new kind such as PR #21's `alibis` fails typecheck until it has its one entry). `reconcile` inserts new rows with their due time, deletes rows the game moved past and leaves the rest alone, so a restart changes no due time. Keys: `round:<n>`, `scheduleMeeting:act-<n>`, `openMeeting:<meetingId>`, `closeMeeting:<meetingId>`, `resolveShakedown:<meetingId>`; never reused once fired.
- **No double, no skip across a crash:** a fired deadline's row is only removed by the reconcile after its events are stored; on boot `settleRunning` (bots settle) reconciles every running game before the 1 s tick starts, so a stale row is deleted before it can fire, and the engine refuses a stale named deadline anyway. A deadline the engine refuses is logged and dropped. A crash between storing and reconciling makes the *next* deadline start from the boot (late, never skipped).
- **Pausing (§4.1):** while a meeting or the Muscle window is open, the round deadline and an emergency's notice are paused (`deadlines.paused_at`, migration 004); afterwards their due time moves on by the pause, so the round keeps the time it had left. The act's `openMeeting` is only planned in `awaitingMeeting`, so it is re-sent after another meeting closes.
- **Act meetings (provisional):** "the act deadline" is the act's last round resolving. Auto-scheduled presets (`quick`, `1h`, `3h`) open the meeting then, whatever slot was locked. Group-scheduled presets (`1d`, `3d`, `1w`) open at the locked slot if it is a strict ISO time (never before the act's end; a non-time slot like the bots' `act-1` means "at once"), and if nobody locked one the server sends `scheduleMeeting` with a slot `meetingLeadMs` ahead (1 h / 2 h / 2 h). Strict ISO only: `Date.parse("act-1")` reads it as a date in 2001.
- **Preset numbers (provisional, `apps/server/src/timing.ts`):** round / alibi window / meeting window / emergency notice / Muscle window — Quick 45 s / 15 s / 2 min / 20 s / 15 s (9 × (45 s + 15 s) + 3 × 2 min = 15 min); 1 h 5 min / 30 s / 3 min / 1 min / 30 s; 3 h 17 min / 1 min / 5 min / 5 min / 1 min; 1 d 2.25 h / 15 min / 10 min / 30 min / 5 min; 3 d 7.5 h / 20 min / 20 min / 1 h / 10 min; 1 w 17 h / 1 h / 20 min / 2 h / 10 min. Rounds run their full length even when everyone has moved (ending early would leak), and the Muscle window always runs in full (it is set once, a cancel never touches it). Host-set window length and quiet hours are not settings yet.
- `buildServer({ tickMs })`: unset means no interval (tests call `app.scheduler.tick()` on a fake clock); `main.ts` passes `TICK_MS` (1 s).
- **Failures (PR #22 review):** `live.system` throws `SystemRefused` only when the engine refuses. A refused deadline is dropped and the game re-planned (`live.settle` → `reconcile`). Any other error (database, bots) keeps the row and retries it on later ticks with backoff (1 s, 2 s, 4 s … up to 60 s; memory only). So a transient failure delays a deadline but never skips it.
- **Bots are deterministic across restarts (PR #22 review):** each decision gets a fresh RNG seeded from (hidden game seed, seat, SHA-256 of the view it acts on) instead of one long-lived stream per bot. The hash of the last view each bot acted on is stored in `seats.bot_seen` (migration 005). Both were 003/004 on the branch until chat took 003; `migrate.ts` renames those versions in `schema_migrations` and the SQL uses `if not exists`, so a dev database that applied the old names migrates cleanly, so a rebuilt server neither acts again on that view nor skips a change. With the same seed and deadlines, a run restarted before every step gives the same log as an uninterrupted one (QA test).
- **Alibi deadline (PR #21):** after a round resolves the game sits in the alibi phase until `advance { kind: "alibis", round }`, planned `alibiMs` after the round resolved (key `alibis:<n>`; pausable, so an emergency during the alibi window pauses it). Round lengths were shortened to make room for it.

The `mole` config field is now the saboteur setting (same values). - **Perks (§8.3):** a token in `roleState.perks`, granted by a private `perkGranted` (no role earns one yet; tests use `perks.testkit.ts`), spent with `useAbility` (a private `perkUsed`; refusals keep the token). One small function per perk in `perks.ts`. Provisional details: Peek any time; **Shield spent by itself** at the next passed shakedown of its holder (public `shakedownCancelled` as for the Muscle; a Muscle cancel first keeps it); +Vote once per meeting while one is open (+1 weight to the result, not the tally or quorum); Ballot while a meeting is open, refused in Open mode; Tail while planning, one per round (Power cut blinds it, a loop doesn't); Alibi stamps only a **true** alibi for the latest resolved round, as a public `alibiVerified`; Recharge resets this act's uses and gives back one use this game, refused if nothing is used; Rig draws two different cards for the next round (first flips by default, `rigPick` chooses, private `rigPicked`), several players may rig the same round (no refusal, so it can't hint at who holds a Rig, e.g. after a Double-cross; PR #25 review) and the oldest Rig's pick flips; a loser only learns, at the flip, that someone else rigged.

- **Shakedown window:** opens whenever any role that could be dealt (pool + saboteurs) is a Muscle or lists `"shield"` in `RoleDef.earns` (new optional field; R2/R3 fill it), so a window never shows that a Muscle or a Shield exists.
- **Perks stay with the player in a Double-cross** (they were earned, not dealt); role uses still travel with the card.
- **Bots:** `expectedMoles` now reads `darkSideOdds` (the chance a saboteur is dealt). Bots don't spend perks yet (R4).

### 2026-11-01 — Chat server (M2-8a)
- **Server-side only, over the game socket** (design §12.1): `chat_messages` (migration 003; not engine events, so the engine and replays are untouched). Client `{ chat: { to?, text } }` or `{ chat: { to?, evidence: seq } }`; the reply is `{ ok }` / `{ rejected, reason }` like a command, run under the game's lock so it stays in order with views. Unknown fields (a forged `from`) are refused; the sender is the socket's seat.
- **Delivery:** a crew message goes to every connected seat; a DM only to its two players' sockets; everyone else gets `{ dmNotice: { from, to, at } }` when `settings.dmNotices` is on (default), and **no frame at all** when off, so nothing about it shows, not even timing. On every (re)connect, after the first view: `{ chatHistory: { messages, dmNotices } }` (crew + your own DMs; notices for others' DMs only if on; latest 200 each).
- **Ids are random UUIDs**, never the order column: a counter would let anyone count the DMs they can't see (with notices off).
- **Evidence cards:** the client names a `seq` only; the server looks it up in the sender's own `viewFor().caseFile` and copies `{ type, payload }` (the event without `type`, `visibility` and `seq`), `verified: true`. A ledger seq, an unknown seq or a sent-in event object is refused, so nobody can share someone else's entry or forge one. Typed text is always `verified: false`.
- **(provisional)** Secret-mode ballots (`secret` visibility) can't be shared as evidence: secret voting would mean nothing if a ballot could be proven on demand (and could then be demanded). DMs to yourself, to a bot (bots don't read chat yet) or to an unknown id are refused.
- **(provisional) Limits** (`settings.ts`): 500 characters (code points) after trimming, CRLF → LF; control characters other than newline/tab and bidi overrides refused; 8 accepted messages per player per 10 s (sliding window on the injected clock, in memory). Text is plain text, stored and sent as typed; clients render it as text, never HTML (M2-8b).
- **Ballots while the vote is open (PR #24 review):** in hidden-then-revealed mode a `voteCast` can be shared only once its meeting's `meetingClosed` is on the sender's ledger (then the ballots are public anyway); a `voteSealed` never can (it is a ballot for a meeting still to come; its cast ballot can be, after that meeting). Otherwise "hidden while voting" would mean nothing, since a provable ballot invites bandwagoning and pressure to prove it.
- **Invisible text is empty (PR #24 QA):** the emptiness check uses the nickname rule (`hasVisibleText` in `settings.ts`, now shared): after NFKC, default-ignorable and format characters (ZWJ, LRM/RLM/ALM, tag characters …), the Hangul fillers, the braille blank, combining marks and whitespace are removed, something must be left. Text is still stored as typed. A run of more than 8 combining marks (`CHAT_MAX_MARKS`, ignoring invisible characters in between) is refused. The rate limiter forgets senders with nothing in their window, swept at most once a window.
- Chat stays open after the game ends. Bots don't chat yet.

### 2026-11-01 — Live game channel and server bots (M2-3)
- **Dependencies:** runtime `@fastify/websocket` (wraps `ws`; m2-plan §1), dev `@types/ws` (its types import `ws`). Tests use its `injectWS()`, so no port and no extra client library.
- **`GET /games/:id/ws`:** signed in by the session cookie and checked before the upgrade, as plain HTTP: 401 signed out, 404 not seated or not started (a lobby game is "not found" here too). The seat comes from `playerIdOf`; any `player` in a client command is overwritten. Only the ten player commands are accepted (a typed table, so a new one fails typecheck until listed); `advance` and `scheduleMeeting` are refused like unknown types. A message over 16 KiB closes the socket (`ws` code 1009).
- **Protocol:** client → `{ cmd, id? }`; reply `{ ok: true, id? }` or `{ rejected: true, reason, id? }` to that socket only (`id`, a string ≤ 64 or a number, is echoed so a client can match replies; replies also keep message order). Bad JSON, binary frames and a missing `cmd` are refusals too; the socket stays open. Server → `{ view }`: the whole `viewFor()`, once on connect and then after changes.
- **A view is pushed only when it changed** (the last text sent per socket is kept). A hidden action (a move, a sealed vote) therefore sends nothing to anyone who can't see it, not even a no-op frame, so its timing can't leak. Same idea as the STATUS rule that a Muscle window always runs its full length; the channel never ends a window or resolves anything early: deadlines only come from `live.system()` (M2-4's scheduler).
- **Bots run in the server process and act only when their own view changed** (PR #20 review/QA): after every change (a client command, a system command, the start, a boot), each bot seat in seat order whose `viewFor()` differs from the one it last acted on acts on it, through the same `handleCommand` + `append` path, repeated while anything changed (at most 20 passes). A bot never sees an unchanged view again, so another player's hidden action (or a flood of them) never gives a bot an extra dice roll, which could otherwise turn into a public act at that moment (a timing leak, and a way to steer bots). It also keeps bot dice at about sim frequency. Ended games drop their bots. Agents are made per game on first need from `seats.bot_personality`, each seeded with SHA-256 of the hidden game seed and its player id (unguessable from the game id, the same after a restart; the RNG restarts after a restart, which only changes bot dice). Refused bot commands are logged and kept in `app.live.botRefusals`.
- **`app.live`** (`system(gameId, command)`, `settle(gameId)`, `settleRunning()`, `closeSession(token)`) is decorated on the Fastify instance for the scheduler and tests. `system` throws when the engine refuses. The lobby's start route calls `settle` after the game's lock is released, so bots make their round-1 moves straight away; if that fails it is logged, not a 500 (the game has started). `onReady` settles every running game, so a crash mid-settle can't leave bots idle.
- **Hardening (PR #20 review):** the upgrade checks `Origin`: no Origin (not a browser) or the server's own host is fine, as is an origin in `ALLOWED_ORIGINS` (comma-separated; default the Vite dev and Playwright servers on localhost/127.0.0.1 ports 5173/5179, whose proxies keep the browser's Origin); anything else is 403. A socket with more than 64 messages waiting for the game's lock is closed with 1008 (a client that waits for replies never gets near it; no clock needed). Signing out closes that session's sockets with 4401. Not done: an open socket outlives its session's expiry (M2-13), and the engine lets one player add any number of public meeting proposals (pushed in every view), a candidate for an engine cap.

### 2026-11-01 — Identity, invites and lobby API (M2-2)
- **Sessions:** a 32-byte random token (base64url) in the `sj_session` cookie (httpOnly, SameSite=Lax, path `/`, 30 days); the DB stores only its SHA-256, and expiry is checked against the injected `Clock`. Not `Secure` yet (local http only). SameSite=Lax keeps the cookie off cross-site posts.
- **Guests (owner decision, guests may host — provisional default):** `POST /auth/guest { nickname }` makes a guest user and session; `POST /invites/:code/join { nickname }` does the same when there's no session, so an invite link + nickname is the whole sign-in. A signed-in user joining keeps their session (nickname optional). The guest user is only made once the join is sure to succeed.
- **`AuthProvider` = a redirect round trip:** `authorizeUrl({ state, verifier, redirectUri, hint })` and `identify({ code, verifier, redirectUri })`. The server makes `state` and the PKCE `verifier` and keeps them in a 10-minute `sj_signin` cookie (path `/auth`); a callback whose `state` doesn't match is refused (400). `returnTo` must match a strict same-site path pattern (one leading `/`, not `//`, only URL path/query characters: no backslash, whitespace or control characters, at most 512 long) and is checked before the session is written; anything else becomes `/` (PR #18 review). The `dev` stub (only with `DEV_LOGIN=1`) sends the browser straight to the callback with `code = hint`, so tests and M2-12 share the flow.
- **`users.google_sub` → `users.external_id`** (migration 002), holding `<provider>:<subject>` (`google:<sub>`, `dev:<name>`) so providers can't collide; null = guest.

### 2026-11-01 — Server skeleton and game store (M2-1)
- **Server dependencies:** runtime `fastify` and `pg` only; dev `@electric-sql/pglite` (tests, and the fallback when `DATABASE_URL` is unset, loaded with a dynamic import) and `@types/pg`. No ORM, migration library, schema validator or `dotenv`, as `docs/m2-plan.md` §1 says. `@fastify/cookie` and `@fastify/websocket` join with M2-2 / M2-3, when they're used. The engine gains no dependency.
- **`json`, not `jsonb`, for the replay inputs** (`games.config`, `game_events.event`, `deadlines.command`): checked on PGlite, `jsonb` re-sorts object keys (`{zeta, a}` comes back as `{a, zeta}`), so a reloaded log would differ from the written one in key order, and any rule that ever iterates a record's keys (tallies by player id) could replay differently. `json` keeps the text byte for byte; a test compares the stored text with `JSON.stringify` of each event. `games.settings` (host's lobby choices, never replayed) stays `jsonb`. Deviation from the plan's wording.
- **Appends:** one `insert … select from json_array_elements($3::json) with ordinality` per batch inside a transaction that also updates `games.status`; the `(game_id, idx)` primary key makes a second writer at the same position fail the whole batch. The state is folded with `applyEvent` before writing, so an event the engine can't fold is never stored.
- **Migrations:** the whole run is one transaction under a Postgres advisory lock, so a failing file leaves nothing applied and two starting servers (or parallel test files on one database) don't race. Versions are file names; two files with the same number are refused.
- **Local Postgres:** `scripts/db.sh` runs a trust-auth cluster on 127.0.0.1:5433 in `.pgdata/` (as the `postgres` user when run as root); `docker-compose.yml` publishes Postgres 16 on 127.0.0.1:5433 for Karthik's machine. 5433 avoids clashing with an existing local Postgres.
- **Defaults:** the server listens on 127.0.0.1:3000 (`HOST=0.0.0.0` for phones on the LAN); PGlite persists to `.pglite/` so a dev restart keeps games.
- **Start-up errors (PR #16 QA):** a blank `PORT` or `PGLITE_DIR` means the default (like `HOST`); otherwise `PORT` must be digits only, 1–65535 (so `0x50`, `1e3` and `0` for a random port are refused). A bad setting or an unreachable / malformed `DATABASE_URL` ends start-up with one line (`StartupError`; the URL is shown as host:port/db, never its user or password) and exit 1. `pgDb` listens for the pool's `error` event (an idle connection dropped by a Postgres restart would otherwise kill the process) and discards a client whose rollback failed.

### 2026-11-01 — Simulator CLI and content overrides (M1 task 10)
- **Content overrides (answers the PR #1 deferral):** `GameConfig.contentOverrides` (optional, null = shipped content) replaces numbers only: room `loot` / `heatPressure` / Deposit-box `capacity`, `heat`, `checkpoints.perPlayer`, `shakedown`, and per role `stashMultiplier` / `perLootOverFinalTarget` plus the role's own power number (Lookout `extraRooms`, Fence `perAct`). - **Simulator (`apps/sim`, node built-ins only):** `pnpm sim -- --help`. N games *per player count*; game `i` at `n` players has seed `<seed>/<n>p/<i>`, so a run is reproducible and any single game can be replayed from its seed. The bot mix is weights: each personality gets its whole share of seats, leftover seats go to the largest remainders with ties broken by a seeded shuffle, then seats are shuffled (no list- or seat-order bias). Per-game `games.csv`, per-seat `players.csv`, `games.json` and `summary.json` go to `sim-output/` (gitignored), resolved from where `pnpm sim` was typed.
- **Metric definitions (provisional, design §17.4 leaves them open):**
  - *Heat-bust share* = Heat failures ÷ failures.
  - *Pocketing bands* by pocketed ÷ looted over the game: honest ≤ 10%, moderate ≤ 40%, heavy above. Insiders are left out (they can't pocket). Win rate is over all games, so a heist sunk by pocketing counts as a loss.
  - *Shakedown accuracy* = shakedowns that weren't clean (the target held at least the clean threshold) ÷ shakedowns: the game's own verdict. Also reported: the target had pocketed anything since their last shakedown (clean-target compensation stays in the stash, so a repeat target can be "not clean" without pocketing).
  - *Role / personality win share*: joint winners share one win; role share is over seats in successful heists, against the fair share 1 ÷ crew size (mean over those seats). Mole win rate is over all games.
  - *Standings at a checkpoint* come from the engine itself (PR #10 review): the log is folded with `applyEvent` and ranked with `ranking()` after each `checkpointChecked` (so after that act's shakedown, scored as at the end). Leaders are `leadersOf(ranking)`: tied on score *and* both tie-breaks, as joint winners are. The sim re-implements no rule.
  - *Comeback*: successful games with a sole Act 1 leader (top score above 0), and how often that leader wins. Target < 50%. Games still fully tied after the tie-breaks are left out (PR #10 review: counting a win when any tied leader won inflated the rate).
  - *Decided early*: of **successful** games, those won by the sole Act 2 leader with a lead of at least half the most one player could add in Act 3 (3 rounds × best room loot × best stash multiplier). Successful games only, like comeback and role shares, so it doesn't fall as task 11 lowers the success rate (PR #10 review). The max-gain proxy ignores Act 3 clean compensation and Insider surplus.
  - *Heavy pocketing target* is the design's "< 50%" ("should lose more often than it wins"); honest vs moderate is the design's "moderate wins more often than honest".
  - *Mole win rate* (task 13): games a Mole won ÷ games with a Mole dealt (was "n/a until Mole powers").
- **Overrides keep crowded loot ≤ loot**: a Deposit-box override (or a loot override on its own) that makes the crowded yield higher than the listed loot is refused, since `checkMove` bounds a pocket by the listed loot (PR #10 review).
- **`--out` is checked before any game runs**: empty is refused (it would write into the directory pnpm ran in; use `--no-files`), and a path that is a file, or an output name that is a directory, is a clean error (PR #10 QA).

### 2026-11-01 — Bots (M1 task 9)
- **`viewFor` returns a deep copy (task 8 review).** Views used to share objects with the game state (rooms, phase, proposals, the log's events), so a bot that wrote to its view changed the real game. `viewFor` now copies its result with a small plain-data copier (`structuredClone` made the leak tests about 4× slower). - **`Agent` is `{ player, act(view) → PlayerCommand[] }`.** It gets only its own `PlayerView`, is asked again whenever the view may have changed, and returns `[]` when it has nothing to do (so it decides from the view whether it already moved, posted its alibi, accepted a proposal or voted). - **Suspicion is rebuilt from the view each time** (no hidden bot memory): per resolved round, the shortfall (others' claimed rooms' loot minus what the others really handed in, using the bot's own split) is shared among who could have taken it, weighted by claimed loot + 1; alibis that contradict the bot's sighting, Security or Lookout results add a lot; being seen where claimed subtracts a little; no alibi once its window has closed adds some; a Server-room count of nobody else pocketing clears the round; a shakedown resets the target's score (low if clean, slightly raised if not). Weights are `SUSPICION_WEIGHTS`, shared by all personalities.
- **Opportunist (provisional):** moves are simultaneous, so a bot can't know in advance that it will be alone. The Opportunist pockets at a medium rate and only *lies* about it when it turned out nobody was in its room. The cover-up alibi is the richest room whose loot is no more than what it really handed in, so the claim adds up.
- **Not yet:** structured chat lines and evidence cards (no chat in the engine), sealed votes (bots are always present), bandwagon voting in Open mode.
- **`runBotGame(config, agents)`** in `packages/bots` plays a game to the end with a stand-in scheduler: each step every agent acts in seat order, then one deadline passes (close the open meeting, open a called emergency, resolve the round, or open the act's meeting, with a server-picked slot if nobody locked one in). Seats without an agent get default moves. Refused agent commands are returned, not thrown; the tests require none.

### 2026-11-01 — viewFor (M1 task 8)
- **`seq` numbers what the player can see, not the full log (replaces the task 1 choice).** With full-log indexes, the gaps between a player's own entries counted hidden events: the gap between your loot split and your room sighting told you whether the Fence used the safe, and its position among the round's events how many players before you sat in Security or used the Lookout power; gaps during a meeting counted hidden ballots. Same reason meeting ids never use the log length. Now `seq` is the index among the events the player can see during the game (public, plus private/secret to them). Ledger and case file share it, it has no gaps, and new events always get higher numbers, so one "last seen" cursor per player works all game (§13). `reveal.log` numbers its own stream the same way, so it has no gaps for others' secret ballots either.
- **Ledger and case file are narrowed by type:** `LoggedEvent<PublicEvent>` and `LoggedEvent<CaseFileEvent>` (`WithVisibility<E, V>` in `types/view.ts`), so client code can't mistake a case-file entry for a public one. After the game they stay as they were; the reveal is the separate `reveal.log`.
- **The view also carries `proposals`** (public, §11.1), so a client or bot can accept one without rebuilding them from the ledger. The open meeting's details (kind, act, who called it) stay in the ledger (`meetingOpened`, `emergencyMeetingCalled`).
- **`viewFor` throws for a player who isn't seated.** Unlike commands it isn't fed untrusted input: the server asks for the authenticated player's own seat.
- **"While you were away" input:** `eventsSince(view, seq)` returns the view's events after `seq`, oldest first. It works on a view, so it can't see more than the view. Turning it into a 2–4 line summary is M2.
- **Leak tests:** after every command of scripted games at 2/5/9/12 players in all three vote modes, each player's view must be unchanged when everything hidden from them is changed, removed or added (other players' roles, stashes, safes, moves, ballots, seed, RNG, hidden events). That catches leaked values and leaked counts.

### 2026-11-01 — End of game (M1 task 7)

A role wins a failed heist if its `reasons` include the failure reason (`"heat"` / `"target"`) and, when `needsTopStash`, it is among the top-ranked players (Driver). Every starter role has `null`. The scoring functions take the role table as a parameter (default `ROLES`), so tests plug in Mole/Driver defs today.

### 2026-11-01 — Meetings and votes (M1 task 6)
- **Meeting timing (PM decision, provisional):** a regular meeting opens only after the act's last round has resolved (rounds 1–3, the Act 1 meeting, checkpoint 1). Its slot can be proposed, accepted or server-picked at any time during the act; `advance { openMeeting }` for it is refused until the phase is `awaitingMeeting`, so the server re-sends it then. Emergency meetings can open mid-act; rounds pause (no moves, no round deadline) while any meeting is open, and closing one goes back to planning the same round with submitted moves kept (or back to awaiting the act's meeting). Only one meeting is open at a time; a second `openMeeting` is refused until the first closes.
- **Ids are built from public data only, never RNG draws or the log length** (the log length would let players count hidden events; PR #6 review). Regular meeting `act-<n>`; emergency `emergency-<player>` (unique, since one per player per game); proposal `proposal-<n>`, numbering the game's `meetingProposed` events from 1. Meetings draw no randomness.
- **Scheduling (provisional):** the proposer counts as accepting; a slot locks once more than half the crew has accepted, which emits `meetingScheduled` and drops the other proposals. A slot already proposed this act is refused. Once a slot is locked, `proposeMeeting`, `acceptMeeting` and `scheduleMeeting` are refused. `scheduleMeeting` must name the act being played.
- **Emergency meetings:** one per player per game, callable in planning or while the act's meeting is awaited, not while a meeting is open; only one may wait in its notice period at a time (the notice period is the server's). A pending emergency survives the act's meeting and opens in the next act. It can shake someone down (with the current act's numbers) but has no checkpoint.
- **Ballots (provisional):** skip, or shake down another player — not yourself, since a clean player could otherwise collect compensation by voting for themselves. A later ballot replaces the earlier one. Ballot visibility: `open` public, `hiddenThenRevealed` private (all ballots go public in `meetingClosed`), `secret` `secretTo()` with `meetingClosed.ballots: null`. `voteSealed` is private, or secret in Secret mode.
- **Sealed votes (provisional, answers the PR #1 review):** a sealed vote has no meeting scope; it counts in the next meeting that opens, regular or emergency, and is used up. It is cast as a `voteCast { sealed: true }` right after `meetingOpened`, so in Open mode it is public from the start of the window, and a present player overrides it with a live vote. Sealing again replaces it; it can't be withdrawn (to abstain, turn up, or let it be used).
- **Tally:** quorum is ballots × 2 ≥ crew size; a shakedown needs target votes × 2 > ballots cast; otherwise `skipped` if skips × 2 > ballots, else `noMajority`. Every ballot weighs 1 (Smooth talker later). Tally and ballots are in seat order.
- **Shakedown:** the stash (never the safe) is revealed and taken; below `cleanBelowPerAct` × act it's clean and the target is paid `compensationPerAct` × act. The numbers are `JobDef.shakedown` (3 and 5) so simulator content overrides can tune them with the other job numbers. **Compensation is capped by the Haul (provisional)**, so the Haul never goes negative.
- **Checkpoint (§11.4):** `closeMeeting` of a regular meeting emits `meetingClosed` → `shakedownResolved`? → `checkpointChecked` → then `copsRaided` + `gameEnded` if the missed-checkpoint +15 takes Heat to 100 (clamped once; `heatPenalty` is the change after clamping), else `roundStarted` for the next act, or after Act 3 (no Heat penalty) `gameEnded` success / failed `target`. Ranking and winners stay empty until task 7.
- **No resume point in `MeetingState`** (`resumeRound` removed): the phase after a meeting follows from `round` and `resolvedRound`. **Commands are refused in the `setup` phase.**

### 2026-11-01 — Round loop (M1 task 4)
- **`handleCommand(state, command)` is the one entry point** for commands. It returns `{ ok: true, state, events }` or `{ ok: false, reason }`. Commands arrive as untrusted JSON, so any bad input is a rejection that leaves state untouched, never a throw: wrong phase, unknown player, room not in play, a split that isn't a whole number from 0 to the room's loot (NaN, fractions, strings, Infinity), Security without a watched room, a watch from outside Security, an ability the role doesn't have. The stored move is normalised (unknown fields dropped).
- **`rngAdvanced` is automatic.** Handlers draw only through the `Draw` they're given; `withRng` appends `rngAdvanced` after their events if anything was drawn, and discards the draws on a rejection. The round loop itself draws nothing.
- **Setup opens round 1.** `setupEvents` now emits `roundStarted { round: 1 }` (before the final `rngAdvanced`), so `createGame` returns a game in planning. No separate "start" command.
- **The default room is content** (`JobDef.defaultRoom`, `"lobby"` for the bank), since other jobs may not have a Lobby. **Rounds per act** is `ROUNDS_PER_ACT` (3) in content.
- **Split bounds:** a move's `pocket` may be 0 to the room's listed loot when submitted, and is capped at the real yield when the round resolves (crowded Deposit boxes pay 3). The Insider's move is refused if `pocket > 0`, and resolution treats the Insider's pocket as 0 regardless.
- **Lookout:** the ability is `{ kind: "lookout", rooms }`, 1 to `extraRooms` distinct rooms in play (content says 1). This replaces the single-room shape, so the content field means something. It's optional each round, and can name any room in play.
- **Watch results leave out the watcher.** Security and Lookout results (`roomWatched.seen`), like room sightings, list the *other* players in the room.
- **Fence safe (provisional):** the deposit happens after this round's split, from the stash including this round's pocket. The submitted amount must be 1 to what's left of the per-act cap (5); the amount actually moved is also capped by the stash, and `abilityResolved` reports the amount that moved. The allowance resets at the first round of each act.
- **Heat:** baseline + room pressure is rounded, added, then clamped to 0–100 once (`roundResolved.heatDelta` is the change after clamping, so Rooftop at Heat 0 shows 0). Events and the missed-checkpoint penalty must join that single clamp when they land. Heat at 100 emits `copsRaided` then `gameEnded { failed, heat }`; the ranking is left empty until task 7.
- **Acts:** after an act's last round the phase becomes `awaitingMeeting { act }` (also after round 9, for the final meeting); task 6 starts the next act. Server-room `pocketCount` counts players who kept anything this round.
- **Player-keyed scratch data uses `Map`**, because player ids are host-chosen strings (a seat called `__proto__` works).

### 2026-11-01 — Seeded RNG and setup (M1 task 2)
- **RNG algorithm: sfc32, seeded by hashing the seed string with cyrb128**, then 12 outputs discarded. Small, fast, 128-bit state, passes PractRand, and simple enough to write in-repo (no engine dependency). `RngState.words` is the four sfc32 words as unsigned 32-bit integers. A golden-value test pins the output, because changing the algorithm changes every old log's draws.
- **How RNG state is rebuilt on replay (deferred from PR #1):** `rngSeeded` sets the RNG from the seed, and any command that draws random numbers ends its events with a reveal-only **`rngAdvanced { words }`** carrying the RNG state after its draws. The fold just copies the words, so replay never re-draws and the fold never needs to know how many draws a rule makes. Being reveal-only, the state is in no player's view during the game (it would let them predict draws); after the game it is harmless, like the seed. Rejected: putting the state on the random-consuming events themselves (`roleDealt` is private and other draws may land on public events, so it would leak), and replaying from commands (breaks "state = fold over the log").
- **Rooms are not random:** they come straight from the player-count tiers in content (§6.2).
- **Role deal (provisional):** Moles first (by the Mole setting), then distinct roles drawn at random from the pool (each at most once), then Rookies for any seats left; the resulting deck is shuffled and dealt in seat order. So 4 players in starter mode get one of each starter role, and 12 get Lookout, Insider, Fence and nine Rookies. The Mole is never a pool role; it is controlled only by the Mole setting.
- **Mole count (provisional):** 2–4 players: never. 5–8: off 0, maybe 0 or 1 (50%), on 1. 9–12: off 0, maybe 1 or 2 (50/50), on 2. Design §8.1 says "1 or 2 Moles" at 9–12 without saying how the host setting maps onto it; the host's "off" is respected at every size. Numbers live in `MOLE_RULES` in content.
- **Starter mode requires `mole: "off"` and `eventsEnabled: false`.** `validateConfig` rejects any other combination instead of quietly ignoring it, so `gameCreated` and the config never claim a Mole or events that a starter game doesn't have (§8.1). (PR #2 review; PM call.)
- **`validateConfig(config: unknown)` returns a list of errors** (empty = valid) instead of throwing, and checks the shape as well as the rules: enum values (`mole`, `voteVisibility`) by membership, `job` by own key only (`Object.hasOwn`), booleans and strings by `typeof`. The M2 server will receive configs as untrusted JSON. `setupEvents` throws with all the errors joined. No schema library. (PR #2 QA; PM call.)
- **Host role pool:** empty means the content default (only the starter roles exist so far). Duplicates, unknown roles and the Mole are rejected. Starter mode ignores the pool.

### 2026-11-01 — Core type choices
- **Each event type fixes its own visibility in the type system.** For example, `roleDealt` can only be private and `rngSeeded` can only be reveal-only, so a secret can't be logged as public by mistake. `voteCast` is public, private or secret depending on the vote-visibility setting; `voteSealed` is private or secret.
- **After the game ends, private and reveal-only events become visible to everyone** (`canSee`), which is what the reveal needs (§13). **Secret events never do.** A fourth visibility kind, `secret` (`secretTo(player)`), is visible only to its player, during and after the game. It is used only for ballots (`voteCast`, `voteSealed`) in *Secret* vote mode, so "only the tally is ever shown" (§11.2) holds at the reveal too. A future Informant role would be granted these explicitly by `viewFor()`, not by `canSee()`. `PlayerView.reveal.log` is therefore a filtered list of `{ seq, event }`, not the raw log. Unknown visibility kinds fail closed, before and after the game. (QA finding on PR #1; PM decision.)
- **A move's split is stored as `pocket`** (the amount kept), not the amount handed in. Real yields can change after submission (shared Deposit boxes, events), so `pocket` is capped at the actual yield, and "hand everything in" is simply `pocket: 0`. Design §5.1's rule is unchanged.
- **`GameConfig` holds only settings that change the rules.** Session length, deadlines, meeting window length, quiet hours, pause/extend and bot replacement belong to the server, because the engine has no clock.
- **The seed never appears in a public event.** `gameCreated` is public without the seed; the seed goes in a reveal-only `rngSeeded` event.
- **Only resting phases are modelled:** `setup`, `planning`, `awaitingMeeting`, `meeting`, `ended`. Resolving, Checkpoint and FinalCheck from §17.2 happen inside one `advance()` and leave only events behind. A meeting that is scheduled or called but not yet open is **not** a phase, because it can coexist with planning: it lives in `GameState.scheduledMeeting` (regular) or `pendingEmergency` (in its notice period, §11.1). Both carry a `meetingId`.
- **`advance` names the deadline that passed:** `round`, `openMeeting { meetingId }` or `closeMeeting { meetingId }`. During planning the round deadline and an emergency notice period can both be pending, and the engine has no clock to tell them apart. The engine rejects a deadline that isn't pending.
- **The server picks a regular meeting slot with a `scheduleMeeting { act, slot }` system command** when nobody locked one in by the act deadline (§11.1). It emits `meetingScheduled` with `proposalId: null`.
- **Meeting time slots are opaque strings** that the engine stores and compares only for equality, never reads as a time.
- **Views carry log positions:** `ledger` and `caseFile` entries are `{ seq, event }`, where `seq` is the index in the full log, for "since seq N" recaps (§13) and evidence cards (§12.1). *(Superseded in task 8: `seq` now counts only what the player can see.)*
- **`meetingClosed.tally` is `{ skip, targets }`**, so no player id can collide with "skip".
- **A ranking's `stash` includes the Fence safe** (the safe protects loot from shakedowns; it is still the Fence's loot).
